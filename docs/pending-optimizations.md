# 待优化：搜索来源、检索复用、subagent 派发

Date: 2026-09-22
Status: 待做。三件都还没改代码。依据是当天两轮「港口拥堵 / 钠电 / CBAM」实测。

相关文档：[后续功能](agent-system-followups.md) 第 1 节（搜索已接上）、第 4 节（subagent 已接上）。

---

## 1. `web_search` 换来源

**现状。** 生产只有 Tavily（`WEB_SEARCH_PROVIDER=tavily`）。一次 `web_search` 向 `https://api.tavily.com/search` 发一个 POST，没有失败重试，也没有第二家提供商。配额用完时工具返回 `search quota exceeded`，模型只能停搜或继续打同一家。

**问题。** Tavily 额度很容易被一轮研究打满。两轮对话里子任务合计约 900 次搜索（第一轮 12 个子任务 531 次，第二轮 8 个 368 次），查询几乎都不重复。余额或配额一尽，还在跑的 loop 直接失败，报告停在开场白。

**要做。** 搜索后端可以换成别的来源，或按顺序换一家。换的时候保持现在的工具形状：失败仍是 tool 错误，命中仍进 `sources/` 账本，测试仍可用 `mock`。具体接哪一家另定，本文不选供应商。

## 2. 派出 subagent 之后搜索偏多

**现状。** 不限制每个任务的搜索次数。同一会话的子任务共用工作区，查询会追加到 `sources/ledger.json` 的 `queries`，命中进 `sources/index.json`。这只是事后账本。`web_search` 不会在发出请求前查这本账，提示词也不要求模型先读它。

父任务调用 `spawn_subagent` 后立刻返回，子 loop 的系统提示只有任务正文。子任务看不到父任务已经搜过哪些 query、已经有哪些 `source_id`。孙任务同样从零开始。查询字符串稍有不同（中英各一遍、或把上一条结果里的数字再拿去搜）就算新查询，账本对不上。

实测里这就是 900 次的来源，大约是这三道题所需的三到四倍：

- 一个子任务按「每个港口、每个数字」各搜一次。`hub-ports-data` 搜 77 次、只读了 5 篇已保存来源；`freight-rates-frontload` 搜 70 次、一篇都没读。
- 父任务派出下级之后自己继续搜同一范围。`ports` 自己搜了 72 次，五个下级又各搜 40–70 次。
- 同一题跑了两轮，第二轮不继承第一轮的账本用法，等于再搜一遍。

**要做。** 用算法把「已经搜过的内容」变成下一级开搜前能用的输入，而不是靠模型自己想起去翻目录。至少包括：

- 会话内缓存。同一工作区里，已经记录的 query 和已经入库的 url 不再向供应商发请求；命中缓存时把已有 `source_id` 和路径交回模型。
- 递归时显式下发。派发子任务时带上父级已覆盖的 query 和来源目录（或一份短清单），子任务先读这份再决定还缺什么。孙任务接的是子任务的清单，不是空任务。
- 近重复。中英转写、只改一两个词、用上一条摘录里的数字当关键词，应算已经覆盖，而不是新查询。

不做硬性次数上限。目标是同一事实只检索一次，下一级接着缺口搜。

## 3. subagent 派发策略

**现状。** 工具说明只要求调用方自选 `id`、`description`、`max_time`，然后不要在本轮等待。`max_time` 是这次派发的兜底秒数，到点才取消；系统没有默认的短时限，也不再套 turn 上限。子任务系统提示是：只做下面这项任务，边做边把结论写进回答（回答才会进 `subagents/{id}/report.md`），可以再派一层孙，但本 loop 收不到孙的报告。

提示词没有写清楚的策略：

- 什么时候该派、什么时候该自己做。现在模型会把一个大题拆成很多孙，同时自己继续搜同一题。
- 子任务和父任务的范围怎么切开，避免两级搜同一组事实。
- `max_time` 是兜底，不是希望的工作时长。调用方若填得很短（实测里顶层被要求填 180 秒，孙却被填成 3000 秒），父任务先被掐掉并唤醒主 agent，主 agent 读到的是还没写完的 `report.md`。
- 交给主 agent 的只有 `subagents/{id}/report.md`。用 Write 写到工作区根目录的 `report.md` 不会被唤醒轮读到。实测里 `battery` 把约 2.3 万字写到了根目录 `report.md`，`subagents/battery/report.md` 里只剩过程旁白。

**要做。** 把派发策略写进主 agent 和子 agent 的提示，并和上面的检索清单一起给下一级。策略要明确这几条：

- 先划清子任务边界再派。每个 `id` 覆盖一块不重叠的问题；父任务派出后不再检索这块。
- `description` 里带上已知来源和不要再搜的范围，而不是只贴用户原题。
- `max_time` 按这块任务的兜底来填，同级用同一量级，不要一边几十秒、一边几十分钟。
- 结论写在回答里，这样才会进入 `subagents/{id}/report.md`。不要另写一份别的路径上的 `report.md` 当作交付物。
